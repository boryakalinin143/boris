# LIFE MANAGER OS — архитектура

Версия документа: 0.1 (04.11.2026). Покрывает разделы 1–11 исходного ТЗ. Раздел 12 «Autonomous Intelligence» и дальше в исходном сообщении обрезаны, поэтому фоновая работа описана только как точки расширения (см. §9).

## 1. Идея в одном абзаце

LIFE MANAGER OS — центральный штаб, который **не хранит и не дублирует** данные специалистов, а опрашивает их по единому протоколу, складывает в центральную базу только общее (цели, задачи, события, рекомендации, статусы, историю действий) и строит из этого дашборд, брифинги и межсистемные выводы. Каждый специалист (Health OS, Finance OS, …) — отдельное приложение в отдельном репозитории, которое само решает, что и в каком виде он отдаёт наружу. Любое действие центра проходит через Permission Manager.

```
                    ┌────────────────────────┐
   Борис ─────────▶ │  Dashboard / Briefings │   web-интерфейс life-manager-os
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │ CENTRAL AI ORCHESTRATOR│   life-manager-os/src
                    │  ├ Registry            │   кто подключён, где, какая версия
                    │  ├ Connector (HTTP)    │   опрос по протоколу LOS/1
                    │  ├ Permission Manager  │   READ / ANALYZE / PROPOSE / EXECUTE
                    │  ├ Life Intelligence   │   правила + LLM поверх сводок
                    │  └ Central Data Layer  │   цели, задачи, события, аудит
                    └───────────┬────────────┘
        ┌──────────┬────────────┼────────────┬───────────┬─────────┐
        ▼          ▼            ▼            ▼           ▼         ▼
   HEALTH OS  FINANCE OS  COFFEE LAB OS  CHEF OS   TRAVEL OS   … (любые новые)
   свой API   свой API    свой API       свой API  свой API
   своя БД    своя БД     своя БД        своя БД   своя БД
```

## 2. Структура репозиториев

Целевая структура — GitHub-организация `PERSONAL-LIFE-OS` (её создаёт Борис руками: Settings → Organizations → New organization, бесплатный план подходит).

| Репозиторий | Назначение |
|---|---|
| `life-manager-os` | центр: оркестратор, Permission Manager, Central Data Layer, дашборд, брифинги |
| `life-os-infrastructure` | протокол LOS/1 (OpenAPI + JSON Schema), шаблон специалиста, docker-compose/деплой, общие CI-проверки, секреты окружения (только описание, не значения) |
| `health-os` | медицинский информационный центр |
| `finance-os` | финансы |
| `coffee-lab-os` | кофейная лаборатория |
| `personal-chef-os` | питание |
| `travel-os` | путешествия |
| `fitness-coach-os` | тренировки |
| `productivity-os` | задачи, календарь |
| `knowledge-os` | библиотека знаний |
| `home-os` | дом |
| `personal-style-os` | гардероб |

Пока организации нет, всё живёт в папке `life-manager-os/` репозитория `boris`. Переезд — простой `git subtree split`/копирование: папка не зависит от остального репозитория.

Внутри `life-manager-os/`:

```
docs/            ARCHITECTURE.md (этот файл), PROTOCOL.md, PERMISSIONS.md
protocol/        openapi.yaml (LOS/1), manifest.schema.json  → позже в life-os-infrastructure
config/          systems.json (реестр), permissions.json (права по системам)
db/schema.sql    схема Central Data Layer (PostgreSQL)
src/             оркестратор (Node.js 22, без внешних зависимостей)
public/          дашборд
templates/specialist-os/   эталонный специалист: копируешь — получаешь новый *-os с готовым протоколом
test/            тесты протокола, прав и «никаких выдуманных данных»
```

## 3. Почему GitHub сам по себе не даёт доступ к данным

GitHub хранит **код**. Данные живут в работающих приложениях (их базы, их API, внешние источники вроде банка). Поэтому связь центра со специалистами — это не «доступ к репозиториям», а сетевой протокол между запущенными сервисами:

1. Каждый `*-os` деплоится как сервис (локально, на домашнем сервере, на VPS или в облаке) и поднимает API LOS/1.
2. `life-manager-os` знает адреса из `config/systems.json`, а токены — из переменных окружения сервера (`LOS_TOKEN_FINANCE_OS` и т. д.). В репозиторий и в чат токены не попадают никогда.
3. Связь только по HTTPS (или внутри приватной сети: Tailscale/WireGuard). Каждый специалист проверяет токен и scope запроса сам — центр не может «попросить больше», чем специалист разрешил.

## 4. Единый протокол интеграции LOS/1

Подробно — `docs/PROTOCOL.md` и `protocol/openapi.yaml`. Кратко, каждый специалист отдаёт:

| Метод | Что | Минимальный уровень |
|---|---|---|
| `GET /health` | жив ли сервис (без авторизации) | — |
| `GET /api/v1/profile` | манифест: System ID, название, версия, описание, функции, данные, разрешения, статус подключения, последнее обновление, состояние синхронизации | READ |
| `GET /api/v1/summary` | короткая сводка для дашборда, только безопасное представление | READ |
| `GET /api/v1/goals` | цели, за которые отвечает система | READ |
| `GET /api/v1/tasks` | задачи (в т. ч. на сегодня) | READ |
| `GET /api/v1/alerts` | предупреждения и напоминания | READ |
| `GET /api/v1/analytics` | агрегаты для аналитики и недельных отчётов | ANALYZE |
| `GET /api/v1/events` | события календарного типа (тренировка, рейс, дедлайн) | READ |
| `POST /api/v1/proposals` | центр кладёт предложение, специалист показывает его Борису | PROPOSE |
| `POST /api/v1/actions` | выполнить действие из списка `capabilities` манифеста | EXECUTE |

Ключевые правила протокола:

- **Пустые данные — это нормально.** Если у системы нечего сказать, она отдаёт пустой список или `null`, а не правдоподобную заглушку. Центр показывает «Недостаточно данных».
- **Каждое значение несёт `as_of`** (когда оно получено у источника) — так дашборд показывает свежесть и не выдаёт старое за текущее.
- **Чувствительные поля решает специалист.** Health OS отдаёт «напоминание: сдать анализ крови до 15.11», а не результаты анализов. Finance OS отдаёт «расходы на продукты: 112% плана недели», а не транзакции.
- **Версионирование по URL** (`/api/v1`). Новое поле — минорная версия, ломающее изменение — `/api/v2`, центр поддерживает обе на переходный период.

## 5. Permission Manager

Подробно — `docs/PERMISSIONS.md`. Четыре уровня, каждый включает предыдущие:

| Уровень | Может |
|---|---|
| 1 READ | читать profile/summary/goals/tasks/alerts/events |
| 2 ANALYZE | + analytics, сопоставлять данные разных систем, строить отчёты |
| 3 PROPOSE | + создавать предложения, черновики задач и планов |
| 4 EXECUTE | + выполнять действия из белого списка; критичные — только после подтверждения Бориса |

Права задаются **на каждую систему отдельно** в `config/permissions.json`: уровень + белый список действий + чёрный список действий + список действий, требующих подтверждения. Чёрный список сильнее всего: `finance-os` никогда не получит `transfer_money`, даже если кто-то поднимет уровень до EXECUTE.

Проверка двойная: центр не отправит запрос сверх выданного уровня, а специалист отклонит токен без нужного scope. Каждое решение (разрешено / отклонено / ждёт подтверждения) пишется в `action_log`.

Секреты: OAuth или ограниченные API-токены на стороне сервера; центр никогда не спрашивает пароли от банка, почты или ключи в чате, и интерфейс не имеет поля для их ввода.

## 6. Central Data Layer

Схема — `db/schema.sql` (PostgreSQL; для локального старта каркас хранит то же самое в JSON-файле). Таблицы:

| Таблица | Что хранит |
|---|---|
| `systems` | реестр специалистов, последний манифест, статус, время синхронизации |
| `permissions` | уровень и списки действий по системам, кто и когда менял |
| `goals` | цели: название, описание, причина, срок, приоритет, измеримый результат, категория, ответственная система, прогресс |
| `goal_history` | история изменений целей |
| `tasks` | задачи, связь с целью и системой, срок, статус |
| `preferences` | предпочтения Бориса (ключ → значение) |
| `events` | общие события из всех систем (тренировка, рейс, дедлайн) |
| `insights` | межсистемные рекомендации Life Intelligence, с источниками |
| `proposals` | предложения, ждущие решения Бориса |
| `action_log` | история всех действий и решений Permission Manager |
| `notifications` | уведомления |
| `snapshots` | последние сводки систем (summary/analytics) с `as_of` — для недельного сравнения |
| `briefings` | сформированные утренние/вечерние/недельные отчёты |

Чего нет и не будет: медицинской истории, результатов анализов, банковских транзакций. Они остаются в своих системах; в `snapshots` попадает только то, что специалист сам отдал в `summary`/`analytics`.

## 7. Life Intelligence

Два слоя:

1. **Правила** (детерминированные, проверяемые). Пример: событие `trip` из Travel OS в ближайшие 14 дней + бюджет из Finance OS → если `планируемые расходы поездки > остаток бюджета месяца`, создать insight «поездка может нарушить финплан». Правило срабатывает только когда **обе** стороны дали реальные данные; иначе insight не создаётся.
2. **LLM-слой** (Claude API) поверх снимков: формулирует брифинги и ищет неочевидные связи. Получает только то, что уже прошло Permission Manager на уровне ANALYZE, и обязан ссылаться на источник каждого факта. Факт без источника в брифинг не попадает.

Каждый insight хранит `sources` (какие системы и снимки использованы), чтобы на дашборде было видно, откуда вывод.

Примеры из ТЗ, переведённые в правила: Travel × Finance (бюджет поездки), Fitness × Health × Chef (нагрузка и меню), Productivity × Chef × Travel (загруженная неделя → быстрые блюда), Coffee Lab × Finance (покупка оборудования), Knowledge → специалист (передать исследование).

## 8. Дашборд и отчёты

**MY LIFE TODAY** (первый экран): дата, день недели, погода (если подключён источник), главные цели, задачи на сегодня, напоминания, ближайшие события, статус всех систем, важные рекомендации, состояние проектов, блок **GOOD MORNING**.

**LIFE OVERVIEW**: карточки HEALTH, FINANCE, FITNESS, NUTRITION, TRAVEL, COFFEE, KNOWLEDGE, PRODUCTIVITY, HOME, STYLE. В каждой: состояние, последние события, прогресс, задачи, предупреждения, время последнего обновления. Нет данных или система не подключена — «Недостаточно данных». Никаких индексов «качества жизни» и выдуманных оценок.

**Брифинги** (`src/briefing.js`):

- *Утренний* — 10 разделов из ТЗ. Каждый раздел собирается только из реальных ответов систем; пустой раздел так и помечается.
- *Вечерний* — запланировано / выполнено / не выполнено / перенесено / расходы / продвижение целей / что улучшить. Тон конструктивный, без упрёков (это правило зашито в промпт LLM-слоя).
- *Недельный* — сводка по всем сферам + сравнение с прошлой неделей **только при наличии сопоставимых снимков** в `snapshots`.

## 9. Фоновая работа (заготовка под раздел 12)

Оркестратор уже разделён на «собрать» (`sync`) и «показать» (`dashboard`), поэтому фоновая работа добавляется планировщиком без переделки: cron/systemd-timer или GitHub Actions по расписанию вызывает `POST /internal/sync`, затем генерацию брифинга, затем уведомление. Конкретику (частота, каналы уведомлений, что именно проверять) допишу, когда будет текст раздела 12.

## 10. Подключение нового специалиста

1. Скопировать `templates/specialist-os/` в новый репозиторий, заполнить манифест.
2. Реализовать отдачу данных (пока ничего нет — пустые списки, это валидный ответ).
3. Задеплоить, выдать токен в переменной окружения сервера центра.
4. Добавить запись в `config/systems.json` и права в `config/permissions.json`.

Ни оркестратор, ни дашборд менять не нужно: карточка появится сама по `domain` из `config/systems.json` (для `other` — по домену из манифеста).
